## 1. Decisions

| Date | Phase | Decision | Alternatives considered | Why |
|---|---|---|---|---|
| 2026-08-04 | P3 | **The DAG grows a terminal `finalize` task with `trigger_rule=ALL_SUCCESS`, depending on BOTH `gate` and `publish_latest`** | Leave `publish_latest` as the only leaf; or drop its `all_done` rule so a failed gate fails it too | A DagRun's state is decided by its **leaf** tasks, and with an `all_done` leaf every outcome came out green — measured, not theorised: a `run_suite` that died in 6 s produced `state=success`, and so would a real regression breach. BUILD_PLAN's P3 exit is "three consecutive green days", so three empty runs would have satisfied it. Dropping `all_done` was rejected because `publish_latest` must still stamp a verdict on a bad night — that is what keeps a *regression* and a *dead DAG* distinguishable to the PR gate. Depends on `gate` as well as `publish` because a trigger rule sees only **direct** upstreams, so hanging it off `publish` alone would reproduce the bug it fixes |
| 2026-08-04 | P3 | **Cross-namespace pod launching is a `Role` in `evalgate` bound to the `airflow-scheduler` SA, not a ClusterRole and not moving the eval pods into `airflow`** | A ClusterRole + ClusterRoleBinding; or run the eval pods in the `airflow` namespace where the chart's Role already grants pod creation | The chart's `airflow-pod-launcher-role` is namespaced and lives in `airflow`, so it does not reach `evalgate` — the DAG's first task would have failed on a 403 a second after 03:00. Moving the pods instead is not available: they mount `evalgate-models` and `evalgate-results`, and a PVC cannot be mounted across namespaces. A ClusterRole would additionally grant pod creation in `kube-system` for no gain. Verbs are one-to-one with what `KubernetesPodOperator` does, and `pods/exec` is deliberately not among them |
| 2026-08-04 | P3 | **The daily baseline is promoted deliberately: the 2026-08-04 in-cluster 96-case run becomes `results/baseline/run_baseline.json`** | Let the first daily run find no baseline, which the gate treats as a pass | With no baseline the gate prints "no baseline artifact; passing", writes **no verdict file**, and `publish-latest` then records `unknown` — so the end-to-end proof would have exercised everything except the gate, which is the part being proved. The promoted run is the same node, same weights (`llama-server:v1-iter2000:Q4_K_M`), same 96 case ids and 0 errors, so the first daily diff measures run-to-run reproducibility on identical inputs. It carries no `backend` field, which is exactly the historical-artifact case `_assert_comparable` allows |
| 2026-08-04 | P3 | **Adversarial is a `ZeroTolerance(max_regressed_cases=0)` rule, not `Threshold(max_drop=0.01)`. The Suite validator now REJECTS any per-category `max_drop` below the quantum** | Keep 0.01 and document that it means zero tolerance | 24 cases means one case is 0.0417, so 0.01 was 4.2x finer than the smallest possible move: it could never mean "tolerate a small drop", only "tolerate nothing" — and it was read as the former for weeks, including by the person who set it. Stated as a count the rule cannot be misread and cannot silently become sub-quantum if the suite grows. The validator makes the class of mistake unrepresentable rather than merely documented; it fired immediately on the test fixture, which encoded the same defect. `min_score=0.80` was dropped as redundant: zero regressed cases is strictly stricter |
| 2026-08-04 | P3 | **`compare()` refuses a cross-backend or cross-build diff, and the error names both sides, both run ids and both model_refs; the CLI exits 2 rather than 1** | Raise the thresholds above the 0.0043–0.0332 drift so cross-backend diffs are merely tolerated | Raising thresholds would spend resolution the gate cannot spare — 0.0332 gross drift is most of a 2-case (0.0833) budget. Refusing costs nothing instead, because same-backend runs are **exactly** reproducible: v1 re-run hours later gave 96/96 byte-identical outputs and an identical score to 9 dp. Exit 2 separates "a regression blocks this merge" (1) from "this comparison should never have been attempted" (2); a CI log that conflates them sends the reader to the wrong problem. `backend` is declared because nothing the server exposes names it; `build_info` is observed from `/props`, so a llama.cpp bump is caught even if the declaration is wrong |
| 2026-08-04 | P3 | **The PR gate runs no model by default. Escalation to a full run is triggered only by changes to `prompt.py`, `scorers.py` or `loader.py`** | A fast subset of the suite on every PR | A subset does not trade accuracy for speed, it destroys the resolution the thresholds are written in: 12 cases/category makes one case 0.0833, and a gate anyone waits for (<10 min ≈ 5 cases on the node) puts one case at a quarter of a category. **A PR also cannot change model weights** — it changes the renderer, scorers, suite builder and harness, all deterministic and already digest-pinned. Re-running 96 cases per PR would spend 2.90 h measuring something the PR almost never affects. The three named files are the exception, because they move every score and no digest says by how much |
| 2026-08-04 | P3 | **Schedule 03:00 UTC, deadline 6 h, staleness bound 36 h — one decision, not three** | Pick N later, or set it to 24 h | N is derived: `floor = interval (24 h) + worst-case duration (3.8 h) = 27.8 h`. Below that a perfectly current result is marked stale purely because tonight's run has not finished. 36 h leaves 8.2 h over the floor, which buys exactly one named property: **one missed or late nightly run does not block merges; two consecutive misses do** (age passes 48 h). The deadline is 6 h against the **3.80 h sustained** projection, not the 2.75 h a three-case burst suggested — the soak that produced those numbers was itself killed by a deadline set from burst rates at 11 of 12 cases |
| 2026-08-04 | P3 | **The eval task has `retries=0`** | `retries=1`, the usual default for a flaky network task | A retry of a ~3 h task cannot fit inside a 6 h deadline alongside the original attempt, so it would mostly convert a failure into a DeadlineExceeded and lose the partial `--progress-jsonl` evidence too. The staleness bound already tolerates one missed night, so the correct response to a failed run is tomorrow's run |
| 2026-08-04 | P3 | **Inference runs in a separate pod via `KubernetesPodOperator`, never in the Airflow task process** | Run the harness in-process in the task; it is HTTP-bound, not CPU-bound | LocalExecutor runs tasks as subprocesses inside the **scheduler's** cgroup, whose 1000m limit is a hard ceiling on all DAG execution. Even though the eval task only waits on HTTP, hosting a 2.9-hour workload there puts DAG scheduling behind it and couples two budgets that were sized separately. The pod also reuses the exact volume split the Job already proved: inputs readOnly beside the hash-gated weights, results on their own claim |
| 2026-08-04 | P1.4 | **THE PRE-COMMITTED BAR WAS NOT MET.
